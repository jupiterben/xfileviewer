## 修复 bath_day.glb 加载报错（GLB 压缩几何体支持）
- 根因：该模型 extensionsRequired 含 KHR_draco_mesh_compression（Draco）+ EXT_texture_webp；项目 GLTFLoader 未配 DRACOLoader（README 原本注明"暂不包含 Draco/KTX2"），报 "No DRACOLoader instance provided"。EXT_texture_webp/EXT_mesh_gpu_instancing/KHR_materials_transmission 均为 three r169 GLTFLoader 原生支持，无需处理。
- 修复：新增 public/draco/（draco_decoder.wasm + draco_wasm_wrapper.js，从 three examples 拷贝，~250KB，构建时自动进 dist）；load.ts 新增 configureGltfLoader：GLTFLoader 挂 DRACOLoader（decoderPath=/draco/，parseAsync 后 finally dispose worker 池）+ setMeshoptDecoder（EXT_meshopt_compression，自包含模块）；新增 gltfRequiredExtensions 预检，KHR_texture_basisu（KTX2，需 renderer 才能 detectSupport）抛中文友好错误"该模型使用 KTX2 压缩纹理，暂不支持"。
- 测试：load.test.ts 新增 KTX2 拒绝路径用例（构造带 extensionsRequired 的最小 GLB）；208/208 过，svelte-check 0 错误，build 通过（dist/draco/ 就位）。
- 后续候选：KTX2 支持需把 renderer 传入 parseModel（KTX2Loader.detectSupport）；新增压缩扩展时可扩 UNSUPPORTED_REQUIRED 映射表。

## 修复 pnpm ERR_PNPM_TARBALL_URL_MISMATCH
- 根因：pnpm-lock.yaml 中 3 个包（@infloopgame/lib-fbx、@sveltejs/vite-plugin-svelte、@sveltejs/vite-plugin-svelte-inspector）带显式 tarball URL 指向 registry.npmmirror.com，而当前活动 registry 是 Verdaccio http://10.147.17.153:4873（经 ~/.npmrc 配置）；pnpm 11.13.1 校验 lockfile tarball URL 与 registry 元数据（Verdaccio 会把 dist.tarball 重写为自身 host）不一致即报错。
- 修复：sed 把 lockfile 中 3 处 npmmirror tarball URL 的 host 换成 Verdaccio 地址（路径格式一致、integrity 不变、版本锁定全部保留，避免删 lockfile 重解析导致的版本漂移）；未采用错误信息建议的 clean --lockfile 重建路线。
- 验证：pnpm install --frozen-lockfile 通过（24.7s），npm test 207/207。
- 环境事实：本 Windows 机 pnpm 为 11.13.1（非 corepack 锁定的 10.18.3）；registry 指向 10.147.17.153:4873（ZeroTier 地址，本机或局域网 Verdaccio）。lockfile 现绑定该私网地址——其他机器若无 10.147.17.153 访问权，pnpm install 会失败（npm ci 走 package-lock.json 不受影响，install.bat/install_linux.sh 均用 npm）。

## 排查"有几率卡死无响应"（诊断，未改码）
- 根因主线索：Tauri 2 中非 async 命令跑在主线程。项目多个重型命令是同步的：native_video_open（加载 libmpv DLL + CreateWindowExW + mpv_initialize + loadfile，全程持 sessions 锁）、native_video_close（Player::drop 里 mpv_terminate_destroy + DestroyWindow）、open_with::list（COM 枚举 + 图标提取，SMB 盘上可阻塞数秒）、hls_close（kill/wait + remove_dir_all）、video_stream_url（canonicalize，网络盘可长阻塞）。这些全部阻塞 UI 事件循环。
- 确定性长阻塞：HlsTranscoder::start 在持有 jobs Mutex 期间调用 wait_for_playlist（最长 30s，hls_transcoder.rs:80-161）；此期间 hls_close 是同步命令，会在主线程上抢同一把锁 → 打开大视频后快速关闭可复现最长 30s 无响应。evict_lru_by 在 open 持锁期间 drop 旧 Player，同样阻塞。
- 次要问题：scan_dir_files 每个文件发一次 Channel IPC 消息（scan.rs:93-98），大目录 IPC 洪泛；associationController.promptFor 的 Promise 仅靠两个按钮 resolve，overlay 被遮挡时永不返回；native_video_status 100ms 轮询为同步命令，主线程忙时排队堆积。
- 修复方向（go）：open/close/list/hls_close/video_stream_url 改 async + spawn_blocking（HWND 创建留在主线程）；start 的锁范围缩小到 map 增删；Channel 按批次聚合文件列表。
